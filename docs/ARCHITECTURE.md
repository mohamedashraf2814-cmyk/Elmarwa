# البنية التقنية — مستشفى المروة

هذه الوثيقة تشرح كيف بُنيت نسخة العرض، وكيف تنتقل كما هي إلى نسخة إنتاجية على Laravel.

## 1. نظرة عامة

```
┌───────────────────────── المتصفح ─────────────────────────┐
│                                                           │
│  app.js (الموجّه)  ──►  views/*.js (شاشة لكل قسم)          │
│        │                     │                            │
│        ▼                     ▼                            │
│  core/store.js  ◄──── workflow/designer.js (SVG)          │
│  الحالة · الجلسة · الصلاحيات · التدقيق · الإشعارات          │
│        │                     │                            │
│        └────────►  workflow/engine.js  ◄──────┘            │
│                   منطق خالص: تحقق · تنفيذ · محاكاة          │
│        │                                                  │
│        ▼                                                  │
│   localStorage  (في الإنتاج: Laravel API + PostgreSQL)     │
└───────────────────────────────────────────────────────────┘
```

- **لا توجد اعتماديات خارجية.** كل الملفات تُحمّل بوسوم `<script>` عادية بترتيب محدد في `index.html`، لذلك يعمل النظام حتى بفتح الملف مباشرة.
- **مساحة أسماء واحدة** `window.EM` تجمع كل الوحدات.
- **الحماية من XSS:** كل نص ديناميكي يمر عبر `EM.esc()` قبل إدراجه في HTML.

## 2. محرك سير العمل (`workflow/engine.js`)

منطق خالص بلا أي اعتماد على DOM، يمكن تشغيله في Node.js (وهذا ما تفعله اختبارات التحقق)، ويُترجم مباشرة إلى خدمة PHP.

### أنواع العقد

| النوع | الشكل | بشرية؟ | السلوك عند التنفيذ |
|---|---|---|---|
| `start` | كبسولة | لا | بداية المثيل |
| `task` | مستطيل | نعم | ينتظر إنجاز مستخدم بالدور المحدد |
| `approval` | مستطيل زعفراني | نعم | ينتظر قرار «معتمد» أو «مرفوض»، مع خيار فصل المهام |
| `auto` | مستطيل فيروزي | لا | إجراء آلي من قائمة معتمدة، مع إجراء تعويض اختياري |
| `decision` | معيّن | لا | يقيّم شروط الفروع بالترتيب، ثم الفرع الافتراضي |
| `fork` | شريط بنفسجي | لا | ينشئ رمزاً لكل فرع (تنفيذ متوازٍ) |
| `join` | شريط بنفسجي | لا | ينتظر وصول كل الفروع ثم يكمل |
| `timer` | كبسولة متقطعة | لا | انتظار لمدة محددة؛ له مسار «انتهاء المهلة» |
| `notify` | مستطيل | لا | إرسال إشعار (داخلي / رسالة بدون بيانات طبية / بريد) |
| `error` | مستطيل أحمر | نعم | معالجة استثناء أو تصعيد لمشرف |
| `end` | كبسولة لازوردية | لا | نهاية فرع؛ يكتمل المثيل عند انتهاء كل الرموز |

### أنواع الروابط

`normal` · `default` (خلاف ذلك) · `approved` · `rejected` · `error` · `timeout` · أو رابط بشرط:

```json
{ "cond": { "logic": "and", "rules": [{ "var": "esi", "op": "<=", "value": 2 }] } }
```

العمليات المدعومة: `=`, `!=`, `>`, `<`, `>=`, `<=`, `contains`، مع `and` / `or`.

### إعدادات العقدة

كل عقدة تحمل: معرّفاً فريداً، اسماً، نوعاً، والقسم، والدور المسؤول (الصلاحية)، وزمن الخدمة SLA، وسياسة الخطأ (`retry` / `escalate` / `compensate` / `manual`)، وعدد مرات الإعادة، وشروط الدخول والخروج، والإجراء الآلي وإجراء التعويض، والمسار الفرعي.

### قواعد التحقق قبل النشر

- بداية واحدة على الأقل ونهاية واحدة على الأقل.
- لا عقدة بدون مدخل (عدا البداية) ولا بدون مخرج (عدا النهاية).
- كل عقدة يمكن الوصول إليها من البداية، وكل عقدة يمكنها الوصول لنهاية.
- القرار: فرعان على الأقل، فرع افتراضي، وكل فرع غير افتراضي له شرط بمتغير معرّف.
- الاعتماد: مساران «معتمد» و«مرفوض».
- التفرع: فرعان على الأقل. الدمج: مدخلان على الأقل.
- المهام البشرية لها دور موجود، والإجراءات الآلية من القائمة المعتمدة فقط.
- **الحلقات** (مكتشفة بخوارزمية Tarjan) يجب أن تحتوي قراراً أو اعتماداً أو مؤقتاً أو عقدة بإعادة محاولة، وإلا تُرفض كحلقة بلا مخرج.

### نموذج التنفيذ

المثيل يحفظ **رموزاً (tokens)** — رمز لكل فرع نشط — وسجلاً كاملاً للأحداث:

```json
{
  "id": "WFI-01000", "workflowId": "wf_emergency", "version": 1,
  "status": "running | paused | failed | completed | cancelled",
  "vars": { "esi": 2 },
  "tokens": [{ "id": "t_…", "node": "assess", "enteredAt": "…", "via": "e12" }],
  "joins": {}, "visits": {}, "outcomes": {},
  "history": [{ "at": "…", "node": "triage", "event": "completed", "by": "u_tri", "edges": ["e3"], "note": "…" }]
}
```

- العقد الآلية تتقدم تلقائياً حتى أول مهمة بشرية أو مؤقت.
- **حماية من الحلقات اللانهائية:** زيارة نفس العقدة أكثر من 12 مرة تُفشل المثيل.
- **الإلغاء** يشغل إجراءات التعويض للخطوات المكتملة القابلة للعكس بترتيب عكسي (مثل تحرير السرير أو المخزون المحجوز).
- **الإصدارات:** كل نشر يحفظ لقطة كاملة. المثيل يعمل دائماً على لقطة إصداره الأصلي.

## 3. العقل المركزي (`core/hospital.js`)

كل إجراء يعبر بين الأقسام يمر من هنا، والشاشات لا تعدّل بيانات قسم آخر مباشرة:

| الدالة | ما تفعله عبر الأقسام |
|---|---|
| `erArrive` · `erLink` · `erDisposition` | تفتح زيارة طوارئ، تحتسب الكشف، تربط الحالة المجهولة بملف، وتحول القرار إلى طلب دخول أو خروج مع موعد متابعة |
| `apptArrive` · `followUp` | تفتح زيارة عيادة، تحتسب الكشف، وتبدأ مسار العيادات |
| `orderLab` · `labReleased` | تنشئ الطلبات + مهمة سحب للتمريض + مسار المعمل؛ وعند الإصدار تحتسب التحليل وتبلغ الطبيب أو تطلب إقراراً للنتيجة الحرجة |
| `orderRad` · `radReleased` | الطلب للأشعة، والتقرير المعتمد يُحتسب ويُبلغ |
| `prescribe` · `dispense` | فحص الحساسية (تنبيه وليس قراراً)، ثم الصرف: خصم المخزون، طلب شراء عند النقص، مهمة إعطاء للتمريض، واحتساب الدواء |
| `requestAdmission` · `compatibleBeds` · `assignBed` | طلب الدخول، مطابقة أنسب سرير (العزل والجناح)، ثم مهام الدخول للتمريض واحتساب الإقامة وإغلاق حالة الطوارئ |
| `startDischarge` · `dischargeItem` · `finishDischarge` | قائمة خروج موزعة على الأقسام، ثم تحرير السرير وإغلاق الزيارة وترحيل الفاتورة وإنشاء مطالبة التأمين |
| `releaseBed` · `cleanDone` | مهمة تنظيف تلقائية، وعند الانتهاء اقتراح السرير لأول مريض مناسب ينتظر |
| `charge` · `postInvoice` · `balance` | التقاط الرسوم على فاتورة الزيارة المفتوحة، منفصلاً عن الطلب السريري |
| `locate` · `journey` | أين المريض الآن، ورحلته الزمنية عبر الأقسام |

## 4. مساعد التشغيل (`core/insights.js`)

مجموعة قواعد تُحسب عند كل تغيير، كل قاعدة تعيد: المستوى، القسم، العنوان، الشرح، وإجراءً (رابطاً أو تنفيذاً مباشراً). أمثلة: حالة تنتظر الفرز أكثر من 10 دقائق، نتيجة حرجة بلا إقرار (تصعيد بنقرة)، سرير متاح يناسب مريضاً ينتظر (تخصيص بنقرة)، مرضى جاهزون للخروج (بدء الإجراءات للجميع)، صنف تحت الحد الأدنى (إنشاء طلبات الشراء)، نسبة مرضى لكل ممرض أعلى من المستهدف، جهاز معمل معطل يؤخر النتائج.

**حدود صارمة:** المساعد تشغيلي فقط ولا يقترح تشخيصاً أو علاجاً أو جرعة.

## 5. المخزن والصلاحيات (`core/store.js`)

- الحساب الموحد `owner` (المدير العام) يملك كل الصلاحيات. قواعد فصل المهام تبقى، ويتجاوزها عبر `store.breakGlass(rule, fn)` الذي يطلب سبباً ويسجل «اعتماد استثنائي» في التدقيق. باقي الأدوار تُرفض مباشرة.

- `store.can(perm)` تتحقق من صلاحية الدور الحالي.
- `store.guard(perm, label)` ترفض الإجراء وتسجله في التدقيق وتعرض سبب الرفض.
- `store.audit(...)` سجل إلحاقي: المستخدم، الدور، الإجراء، المرجع، النتيجة، السبب، الحالة قبل وبعد، معرّف الترابط.
- صفحة التدقيق تحسب **بصمة متسلسلة** لكل سطر (كل بصمة تعتمد على السابقة) لتوضيح مبدأ السجل غير القابل للتلاعب.

### ضمانات التنفيذ على الخادم

- كل انتقال داخل **معاملة قاعدة بيانات** مع `SELECT … FOR UPDATE` على صف المثيل.
- **مفتاح عدم تكرار** لكل حدث خارجي ولكل دفعة.
- العقد الآلية والمؤقتات تُنفذ كـ **Jobs** على Redis مع إعادة محاولة بتباعد متزايد، والحالة محفوظة في قاعدة البيانات فتستأنف بعد إعادة التشغيل.
- `Policy` لكل انتقال يتحقق من الدور والقسم وفصل المهام.

### الواجهة

ترحيل الشاشات إلى Vue 3 + TypeScript (Inertia أو SPA)، ومصمم سير العمل إلى Vue Flow مع إبقاء نفس شكل العقد والألوان وتنسيق JSON للاستيراد والتصدير (`format: "elmarwa.workflow"`).
